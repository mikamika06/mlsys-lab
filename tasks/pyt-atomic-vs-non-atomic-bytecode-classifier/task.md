## Context

The Global Interpreter Lock (GIL) prevents multiple Python threads from executing Python bytecode instructions at exactly the same instant in standard CPython. This does not mean every source-level operation is atomic.

A source expression can expand into several bytecode instructions. If the interpreter can switch between those instructions, another thread may observe an intermediate state. For a simplified classifier, an operation is considered atomic-under-GIL when its compiled body contains exactly one operation bytecode after removing interpreter scaffolding instructions.

The bytecode sequence is produced by CPython's `dis` module. Let $B(op)$ be the list of relevant bytecode instructions generated for an operation. The classifier marks an operation atomic when

$$
|B(op)| = 1 .
$$

For example, a simple operation that maps to one instruction can pass, while an update such as `x += 1` expands into loading, computing, and storing instructions and does not.

## Task

Implement `classify_atomic_ops(ops)`.

The function receives a list of operation names and returns a dictionary mapping each name to a boolean:

```python
def classify_atomic_ops(ops: list[str]) -> dict[str, bool]:
    ...
```

Supported operation names are:

- `"STORE"`: a local assignment operation.
- `"list.append"`: appending one value to a list.
- `"x+=1"`: incrementing a local integer.
- `"d[k]+=1"`: incrementing a dictionary value with an integer key.

The returned boolean must be computed from CPython bytecode inspection, not from a table of answers. Use the `dis` module to inspect the compiled operation.

Ignore interpreter scaffolding instructions such as `RESUME` and return instructions. Count the remaining instructions and classify the operation as atomic only when exactly one remains.

## Example

```python
classify_atomic_ops(["STORE", "x+=1"])
# Example output:
# {"STORE": False, "x+=1": False}
```

## What the gate checks

The gate builds the expected result using the real CPython `dis` module on the same operation snippets. It compares the submitted classifier output against this bytecode-derived oracle.

A hardcoded answer table is likely to fail because the gate derives the classification from actual bytecode generated by the interpreter.

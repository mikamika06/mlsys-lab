When benchmarking LLM serving architectures, choosing between a fixed request rate distribution (such as a Poisson process) and a maximum concurrency arm design can dramatically alter the observed performance characteristics, bottleneck locations, and saturation points of the system. Engineers frequently rely on raw JSON performance outputs generated by benchmarking utilities like vLLM's serving benchmark tools to evaluate these deployment trade-offs.

However, a recurring issue in our automated performance analysis pipeline is the significant variability and percentile noise present in latency metrics across repeated benchmark runs. When attempting to validate whether a newly introduced serving configuration achieves a target performance shift—such as reliably confirming a 5% latency difference—single-run measurements are notoriously unreliable. Without a systematic way to compute the required number of repeated trials based on variance, or a robust parser that normalizes raw execution logs into a structured comparison table, engineers cannot accurately determine whether an optimization is genuine or merely statistical noise.

Your task is to build a rigorous benchmark processing and comparison module that correctly parses raw vllm-style output JSON, computes the necessary sample sizes to bound statistical noise for percentile claims, and constructs accurate comparative tables between fixed rate and maximum concurrency arms. This will ensure our automated testing framework can reliably assess serving methodology changes without being misled by high-variance tail latencies.

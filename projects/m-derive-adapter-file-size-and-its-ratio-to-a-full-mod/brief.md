We are running into critical issues in our deployment pipeline that are blocking the new targeted-marketing LLM rollout. The training team has been providing LoRA adapters that work phenomenally well in our local evaluation harnesses. In those developer setups, we dynamically attach the adapter weights to the base model at inference time. However, to optimize our serving latency in production, the MLOps team wrote a script to pre-merge the adapters into the base fp16 checkpoint, and subsequently requantize the merged model down to int8 format.

Since rolling this out to our staging environment, we are seeing three major symptoms. First, ops is complaining that the storage footprint of these "merged" checkpoints occasionally balloons well beyond expectations compared to the base weights alone, which should not happen. We need a way to mathematically profile the adapter file size overhead. Second, the model outputs from the merged int8 deployments are producing highly degraded, borderline incoherent text. We are not sure if the mathematical equivalence of our merge operation is subtly broken, or if the merge-then-requantize step introduces extreme numerical errors compared to just keeping the adapter attached in higher precision. Please build a sizing tracker and an error analysis suite to diagnose exactly where the divergence is happening.

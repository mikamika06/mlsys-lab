The Triton inference server cluster deployed in our production environment is experiencing unpredictable response latency spikes and bloated cache footprints during peak traffic periods. Operators have noted that prompt responses are occasionally served from the response cache even when sampling parameters or backend-specific configurations subtly diverge, leading to silent correctness issues and corrupted downstream outputs. Furthermore, telemetry ingestion scripts fail to accurately quantify the net latency savings versus the memory overhead consumed by storing cached completion tokens, making capacity planning impossible. Finally, certain experimental model configurations containing stochastic sampling layers or dynamic request-dependent state are erroneously admitted into the response cache, causing cascading failures and non-deterministic behavior. We need a robust, deterministic implementation of Triton's cache-key hashing scheme, precise latency and memory cost calculations from recorded cache telemetry counters, and a strict safety validator that flags model configurations unsafe for response caching.

# Symptom Brief: vLLM Multi-Tenant KV Cache Leakage and Side-Channel Risks

During recent compliance auditing and benchmark profiling of our hosted multi-tenant vLLM inference cluster, security analysts flagged two distinct operational risks:

1. **Cross-Tenant Block Co-Locating & Invalidation:**
   Requests originating from distinct customer tenants using identical prompt prefixes are occasionally being assigned to shared physical KV cache blocks when standard prefix-caching is active. Despite configuring per-tenant namespace identifiers in the control plane, physical cache allocations reveal that prompt hashes are colliding or bypassing namespace boundaries, allowing Tenant B to reuse cached state generated by Tenant A.

2. **Timing Side-Channel Exploitation:**
   Benchmarking against the multi-tenant endpoint showed significant variance in Time-To-First-Token (TTFT) distributions. Attackers probing the endpoint with candidate prompt strings can infer whether another tenant has previously queried specific text sequences by measuring TTFT latency drops, effectively turning cache hit/miss behavior into an information leakage channel.

Additionally, our infrastructure pipeline currently contains 10 draft launch configurations and docker-compose templates intended for multi-tenant deployment. A security audit is required to inspect these deployment files, identify security misconfigurations (such as shared salts, disabled namespace isolation, or exposed profiling interfaces), and flag all unisolated configurations before production rollout.

Your task is to fix the tenant-isolated block hashing engine, quantify the timing side-channel leakage across TTFT distributions, audit the deployment files, and write a regression test suite that catches cross-tenant cache sharing vulnerabilities.

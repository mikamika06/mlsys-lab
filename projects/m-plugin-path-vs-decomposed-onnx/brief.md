We are debugging a TensorRT plugin pipeline where custom operators bound via the custom-domain mechanism are behaving inconsistently when migrating legacy architectures to newer runtimes. Specifically, in our production inference server, certain models that run fine using explicit TensorRT network definitions fail during plugin resolution when switching between an end-to-end decomposed ONNX subgraph approach and a native IPluginV3 plugin registration pathway.

When we compile our models using the decomposed ONNX path, custom operations are represented as sequences of standard elementary layers (e.g., reshapes, elementwise operations, and reductions) that execute correctly but suffer from substantial kernel launch overheads and sub-optimal memory access patterns. To fix this, we implemented a custom TensorRT plugin to fuse these subgraphs into a single specialized kernel. However, during the transition from legacy `IPluginV2DynamicExt` implementations to the modern `IPluginV3` API ecosystem, several critical issues emerged:

1. Method mapping discrepancies between `IPluginV2DynamicExt` and `IPluginV3` interfaces, particularly regarding metadata serialization, tensor format negotiation, and plugin capability negotiation across distinct builder phases.
2. Custom-domain op to plugin binding audit failures, where parser registrations fail to intercept custom nodes correctly or mismatch input/output data types during network construction from ONNX files.
3. Silent fallback or illegal builder state assertions when dynamic shapes interact with custom plugin creator registries, causing execution crashes or output tensor shape mismatches at runtime.

Your task is to implement the core modules for plugin path vs decomposed ONNX analysis, manage the explicit method mapping and wrapper layers for IPluginV3 transition, and build a rigorous binding audit utility to verify custom-domain op resolution. Finally, you must supply a robust regression test suite that catches any regressions in plugin binding invariants.

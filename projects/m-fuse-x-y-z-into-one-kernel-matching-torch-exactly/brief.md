We noticed a major regression in GPU memory bandwidth utilization during our nightly benchmark runs on Triton elementwise kernels. Specifically, when executing a sequence of three elementwise operations corresponding to the mathematical expression $(x + y) \times z$ on large tensors, the GPU spends an excessive amount of time stalled on high-bandwidth memory (HBM) read and write operations rather than performing actual floating-point computations on the streaming multiprocessors.

Profiling traces reveal that each individual PyTorch operation or naive separate Triton kernel is independently loading input tensors from HBM into SRAM and writing intermediate results back to HBM before proceeding to the next operation. This round-trip latency severely limits performance and prevents our pointwise pipeline from saturating the available memory bandwidth. Furthermore, when writing custom fusion kernels manually, engineers have encountered subtle bugs where mismatched broadcasting strides across the operands lead to completely incorrect numerical results or silent output corruptions that do not match the expected PyTorch broadcast semantics.

We need to implement a fully optimized, single-pass Triton fused kernel that computes $(x + y) \times z$ precisely matching PyTorch behavior across all valid broadcastable shapes, derive the exact HBM bytes saved compared to the un-fused baseline, and construct a robust test suite that catches broadcasting stride mismatches and incorrect tensor indexing.

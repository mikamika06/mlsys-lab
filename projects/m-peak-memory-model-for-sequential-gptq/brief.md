We are getting scattered out-of-memory (OOM) tracebacks during our sequential GPTQ quantization runs, and it's unpredictable exactly when or why they happen. We deliberately quantize the model layer by layer sequentially in order to save GPU memory, but depending on the specific model architecture and the calibration dataset size, the process randomly crashes. Some models fail on the massive MLP layers, others crash on the attention projections, and sometimes just bumping the sequence length of the calibration data takes down the whole quantization job.

We urgently need a reliable peak-memory model that simulates the exact memory timeline of quantizing a single linear layer. A layer goes through specific distinct phases: loading FP16 weights, loading FP16 calibration activations, computing an FP32 Hessian matrix (which scales quadratically with input dimension and is very expensive), and finally producing the compressed 4-bit quantized weights.

By modeling this exact timeline, we can identify exactly which component—weights, activations, or the Hessian matrix—is pushing us over the hardware VRAM limit. Once we successfully know the bottleneck, we can automatically triage the failure: we can suggest `cpu_offload` for massive weights, `reduce_calib_batch` if activations are bloating, or `block_quant` if the Hessian matrix is too large. Implement the memory model and the triage logic to help us dynamically configure the quantizer pipeline.

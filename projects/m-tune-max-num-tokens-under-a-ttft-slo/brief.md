We are observing severe latency spikes and service level objective (SLO) violations when deploying large language models via the TensorRT-LLM backend using trtllm-serve. During peak traffic loads, the time to first token frequently exceeds our hard operational constraint of 500 milliseconds. Investigation reveals that our current configuration uses a naive static batching setup combined with an unoptimized max_num_tokens limit, which leads to excessive queueing delays or memory thrashing under bursty arrival rates.

Switching to a continuous batching model helps mitigate queueing overhead, but simply enabling it without correctly tuning max_num_tokens leaves performance suboptimal. If max_num_tokens is set too high, scheduling large prefill chunks causes severe head-of-line blocking and pushes TTFT past our SLO limit. Conversely, setting it too low underutilizes available GPU compute capacity, severely degrading overall token throughput.

We need a programmatic tuning pipeline that models request queueing, simulates TTFT under continuous versus static batching regimes, and automatically determines the optimal max_num_tokens parameter that satisfies the TTFT SLO while maximizing throughput. Furthermore, we need robust regression tests to ensure our tuning logic and constraint checks cannot be silently broken by future configuration changes.

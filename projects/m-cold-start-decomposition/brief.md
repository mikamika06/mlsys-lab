Our team recently developed a real-time object detection service using ONNX Runtime. When running the service on local MacBooks, the latency metrics look perfectly acceptable. However, after deploying to a new cloud instance equipped with an NVIDIA T4 GPU, we noticed a critical issue. The `requirements.txt` was updated to include `onnxruntime-gpu`, but the production logs show the exact same inference latency as the local machines. Even weirder, there are no crashes or hard errors, just an easily-ignored info log about CUDA which gets completely lost in the noise of other startup messages.

Furthermore, when we tried load testing and autoscaling, we observed that the autoscaler is constantly lagging behind traffic spikes. Upon adding manual trace spans, we discovered that the very first request routed to a newly spun-up container takes nearly 2 full seconds to complete, while subsequent requests to that same container finish in about 15 milliseconds. We need a systematic way to detect when a deployment environment has a conflicting shadowing wheel installed that silently forces a CPU fallback. We also need a reliable profiler to decompose our latency numbers so we can continuously monitor the "cold start" initialization penalty (session creation plus the first-run compilation phase) separately from the "steady state" inference speedup when comparing the CPU execution provider against alternate EPs like CUDA or TensorRT.

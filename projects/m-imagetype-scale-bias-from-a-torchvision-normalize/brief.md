When converting a vision model from PyTorch to CoreML via coremltools, we often receive a pipeline where images are normalized using standard torchvision parameters (mean and standard deviation) in the preprocessing pipeline.

Recently, deploying our image classification pipeline to the edge has exposed a subtle numerical drift in inference outputs. When feeding images directly through the CoreML model, the top-1 predictions occasionally diverge from the original PyTorch model on edge devices, even though the weights were exported directly using coremltools `ct.convert`.

Further investigation points to how the normalization layer is embedded. The standard `torchvision.transforms.Normalize(mean=[0.485, 0.456, 0.406], std=[0.229, 0.224, 0.225])` is frequently left as a separate manual preprocessing step or incorrectly mapped when building the CoreML `ImageType` input configuration, leading to channel-wise scaling and biasing errors inside the input tensor transformer. Additionally, our packaging pipeline lacks visibility into memory savings: we need to systematically compute the exact storage size ratio when switching the exported `.mlpackage` representation between fp32 and fp16 precision to ensure our mobile bundle size constraints are strictly met before deployment.

Your task is to build a utility module in `core_image/` that correctly maps torchvision normalization parameters to CoreML `ImageType` scale and bias attributes, converts a simple CNN with fp32 precision while verifying numeric drift against a reference oracle, and calculates exact fp16-to-fp32 package size ratios. You must also write robust regression tests ensuring that input scaling transformations are never inverted or incorrectly applied.

Our kernel profiling pipeline on the H100 cluster is currently drowning in raw reports and traces, making it nearly impossible for the systems team to quickly spot performance bottlenecks during kernel development. When running deep diagnostics across various attention and GEMM kernels, engineers generate an overwhelming volume of artifacts: Nsight Compute text exports containing raw hardware counter metrics, PyTorch Proton profiler trace logs detailing time spent across named regions, and low-level JSON trace dumps from torch.profiler packed with raw kernel launch configurations and execution metadata. 

Without a clean, programmatic way to ingest and parse these disparate profiling formats, identifying whether a Triton kernel is compute-bound, memory-bound, or occupancy-bound requires manual, error-prone spreadsheet crunching. Furthermore, computing exact percentage time breakdowns per named region from Proton traces or reconstructing block and grid dimensions alongside estimated TFLOPS from torch.profiler json payloads remains a major productivity bottleneck. We need a robust diagnostic toolkit that parses these profiling artifacts directly, classifies kernel bottlenecks based on roofline metrics, calculates region-level runtime percentages, and accurately derives operational intensity and floating-point throughput from raw trace metadata.

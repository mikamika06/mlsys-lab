We have deployed a custom matrix multiply and reduction kernel in our low-level system stack to speed up a core transformer operator, but the performance telemetry is giving us mixed signals. While the kernel executes without errors, profiling captures a near-zero percent L2 cache hit rate when running large problem dimensions, yet the throughput counters indicate severe latency bounds.

When we profile with smaller matrix dimensions that fit entirely into on-chip cache, the kernel achieves near-peak performance. However, scaling the problem size up to production workloads causes the L2 cache hit rate to collapse down to less than one percent, completely neutralizing the benefits of our optimized execution pipeline. At the same time, we have introduced a shared-memory tiling strategy designed to optimize global memory traffic, but we need to conclusively verify whether the measured speedup is genuinely explained by the theoretical reduction in DRAM bytes transferred or if other bottlenecks are at play.

Your task is to diagnose the near-zero L2 hit rate as a working-set-larger-than-L2 problem, implement the necessary profiling and telemetry measurement logic to analyze memory traffic, and verify that the shared-memory tiling optimization accounts for the observed DRAM bandwidth savings and speedup. You must write the analysis code, diagnostic checks, and a comprehensive regression test suite that catches faulty tiling implementations which fail to reduce external memory transactions.

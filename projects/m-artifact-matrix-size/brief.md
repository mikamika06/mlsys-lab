The inference platform team is seeing container registry storage exhaustion and deployment failures across the multi-tenant GPU cluster. When deploying unified TensorRT engine artifacts across heterogeneous worker nodes, the storage required per model build has inflated unexpectedly. Cluster nodes running different container images with minor or patch version variations of TensorRT (e.g. 10.0.1 vs 10.0.3 vs 10.2.0) are either triggering redundant full engine rebuilds or rejecting artifact loads outright due to strict engine header version mismatches.

Operations logs indicate that build pipelines are generating separate engine binaries for every combination of model, precision, GPU compute capability, and TensorRT minor version. When engineers attempted to enable Version Compatibility (VC) to unify engine artifacts across TensorRT versions, several deployment pods ran out of disk space during artifact staging because the memory and storage footprints of version-compatible engines exceeded initial estimates.

We need a systematic toolsuite to compute the artifact matrix footprint across GPU architectures and TensorRT versions, evaluate container patch compatibility to issue surgical rebuild or patch-alias directives, and model the precise breakeven storage cost of version-compatible engines including lean runtime and refit overhead.

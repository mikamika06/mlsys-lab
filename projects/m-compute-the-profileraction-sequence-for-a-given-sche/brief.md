Our team is integrating PyTorch's native profiler into our model training pipeline to track GPU utilization, kernel execution times, and memory allocations. However, we are running into a frustrating instrumentation issue during our distributed runs.

Specifically, when configuring the profiler schedule using torch.profiler.schedule, our automated runs are generating an incorrect number of trace files compared to the total step count we configured. Some training jobs end up with far too many trace files, while others fail to capture the active recording windows entirely, leading to corrupted profiling artifacts or empty trace directories. Furthermore, during a recent debugging session where we suspected a double profiler.step() invocation inside our training loop, the resulting trace file count completely skewed our expectations, making it impossible to correlate step indices with the correct profiler actions (WARMUP, RECORD, RECORD_AND_SAVE, NONE).

We need a robust, deterministic utility module that correctly computes the exact ProfilerAction sequence for any given schedule configuration and step count, safely instruments a standard training loop using schedule and on_trace_ready callbacks to produce precisely the expected number of trace files, and provides a rigorous diagnostic test to catch accidental double step calls by analyzing the emitted trace file count.

We are encountering severe resident set size (RSS) inflation and page fault spikes when exporting and loading large Transformer weight sets on edge hardware with restricted memory budgets. When running our standard inference pipeline, loading multi-gigabyte safetensors files via standard heap allocations (e.g., Python's file read into bytearrays followed by torch tensor creation or direct C++ heap buffers) leads to high peak memory usage, slow startup times, and severe memory fragmentation.

Recently, we attempted to optimize the loader by switching to memory-mapped file IO (`mmap`), allowing the operating system kernel to page weights directly from storage on demand. While this significantly reduced startup latency and initial RSS, profiling downstream execution revealed subtle memory regressions and complex page-in behavior during weight deduplication passes. Specifically, when we perform weight deduplication across multiple model variants or shared layers, the `mmap` approach interacts poorly with copy-on-write semantics and anonymous page allocations, occasionally causing higher-than-expected dirty page counts and unexpected memory pressure compared to traditional heap loading.

Your task is to analyze, implement, and attribute these memory footprint characteristics across both loading strategies. You need to build a comprehensive loader utility that models both `mmap` and heap loading overheads, accurately computes size-regression attributions for specific tensor chunks, and evaluates weight-deduplication savings under both paradigms. You must ensure your implementation correctly tracks memory byte costs, avoids page inflation, and includes robust regression testing to guarantee that your deduplication and loading logic maintains strict invariant bounds.

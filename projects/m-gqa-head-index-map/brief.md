# Мапа індексів голів для GQA

Модель перевели на власний inference-бекенд без флеш-атеншн кернелів — чистий
numpy на CPU для дебагу проблем з якістю. На старій MQA-моделі (одна kv-голова
на всіх) вивід збігається з оригіналом токен у токен. На новій GQA-моделі
(32 query-голови, 8 kv-голів) текст став помітно гіршим, хоча всі форми
тензорів на місці: кеш того ж розміру, голів рівно стільки, скільки в
конфігу. Хтось під час портування розтягнув kv-голови до потрібної кількості
query-голів не тим способом — і жодна перевірка форми масиву цього не
покаже, бо форма виходить правильна в обох випадках.

Треба явно побудувати мапу «яка query-голова читає яку kv-голову», порахувати
на ній оракульну увагу і написати тест, який ловить підміну правильного
групування на хибне.

## Що ти пишеш

`gqa/mapping.py`:

```python
build_head_map(num_q_heads, num_kv_heads) -> list[int]
build_query_groups(num_q_heads, num_kv_heads) -> list[list[int]]
```

`num_q_heads` завжди ділиться на `num_kv_heads` націло; `group = num_q_heads
// num_kv_heads` — скільки query-голів припадає на одну kv-голову. Конвенція —
суцільними блоками: query-голови `[0, group)` читають kv-голову `0`,
`[group, 2*group)` — kv-голову `1`, і так далі (саме так лежать ваги в
реальних GQA-моделях: розкладання kv-голови на `group` послідовних копій, а
не «кожна n-та query-голова»). `build_head_map` повертає список довжини
`num_q_heads`, де елемент `q` — індекс kv-голови, яку читає query-голова `q`.
`build_query_groups` повертає список довжини `num_kv_heads`, де елемент `k` —
відсортований список query-голів, що належать kv-голові `k`.

`gqa/attention.py`:

```python
expand_kv(kv, num_q_heads) -> np.ndarray
gqa_attention(q, k, v, num_kv_heads) -> np.ndarray
```

`kv` — масив форми `(num_kv_heads, seq, head_dim)` (ключі або значення
окремо). `expand_kv` розтягує його до `(num_q_heads, seq, head_dim)` за тією ж
блоковою конвенцією, що й `build_head_map`: рядок `q` результату — це рядок
`build_head_map(num_q_heads, num_kv_heads)[q]` вхідного масиву. `gqa_attention`
рахує звичайну causal scaled-dot-product увагу: `q` форми `(num_q_heads, seq,
head_dim)`, `k`/`v` — `(num_kv_heads, seq, head_dim)`; кожна query-голова
бачить лише позиції `j <= i` тієї kv-голови, яку їй призначає мапа.

## Як перевіряється

Грейдер рахує оракул сам, незалежною реалізацією (цикли замість
векторизації), на кількох конфігураціях голів і кількох випадкових
(фіксований seed) кейсах уваги. Третій майлстоун — твій: пишеш тест у
`tests/test_regression.py`, а ми підміняємо `build_head_map` на варіант, що
роздає query-голови по колу (`q % num_kv_heads`) замість суцільних блоків.
Твій тест має це побачити.

```
mlsys project start m-gqa-head-index-map
mlsys project grade m-gqa-head-index-map --milestone 1
```

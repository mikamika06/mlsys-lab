# Ticket: On-device Core ML model deployment fails memory footprint budget on target hardware

## Symptom
During our recent integration cycle for on-device deployment on Apple Silicon hardware targeting iOS runtime environments, several candidate models packaged as `.mlpackage` artifacts exceeded the strict memory allocation and resident footprint thresholds established by the hardware platform team. Specifically, baseline models retaining full-precision floating-point weights (FP32) occupy excessive storage and active RAM during initial model loading, triggering memory pressure warnings and intermittent instantiation failures in constrained execution environments. Although engineers attempted applying standard weight pruning techniques using basic magnitude thresholds, the resulting serialized package sizes did not reflect the anticipated compression gains, and subsequent attempts to combine structured magnitude pruning with low-bit palettization resulted in invalid metadata structures or inaccurate size estimations that confounded automated build verification pipelines.

Furthermore, engineers lack a reliable programmatic method to derive expected `.mlpackage` file sizes mathematically prior to serialization, leading to protracted trial-and-error cycles during CI builds. Without an automated verification harness that confirms size reductions across chained transformation passes and enforces rigorous invariants on size derivation formulas, regression bugs in compression pipelines go undetected until runtime deployment failures occur on target devices. We require a robust, deterministic Python module set (`coreprune`) that correctly implements magnitude pruning via MagnitudePruner workflows, chains pruning with palettization, accurately computes and verifies size reductions, and provides comprehensive unit tests to catch derivation regressions.

# Ticket: Profiling Discrepancies and Occupancy Bottlenecks in Triton Kernels

We are currently investigating severe performance regressions and lack of diagnostic visibility in our newly integrated Triton kernels across both NVIDIA cluster nodes and local Apple Silicon development workstations.

When executing our flash-attention and reduction kernels on the production cluster, NVIDIA Nsight Compute (NCU) profiles consistently report sub-optimal execution behavior. Specifically, the reported theoretical versus achieved occupancy metrics show a severe disconnect, with hardware execution units sitting idle or under-utilized. Preliminary investigation suggests that kernel execution is constrained by high register usage per thread, but we lack an automated way to parse and analyze NCU metrics to pinpoint whether register pressure is the primary bottleneck throttling our war-group concurrency.

Simultaneously, developers working locally on macOS without CUDA hardware are unable to utilize standard profiling tools. When attempting to run diagnostics with TRITON_INTERPRET=1, the interpreter executes instructions but fails to produce a structured per-block timing table or execution trace. Without this local block-level execution timing breakdown, developers cannot debug block scheduling behaviors, divergence issues, or latency bottlenecks prior to submitting code to the cluster.

We need a robust programmatic analysis module that can ingest kernel configuration parameters alongside NCU profile metrics to accurately flag register-pressure-limited occupancy, combined with an interpreter-backed profiling helper that constructs clean per-block timing tables under interpreter mode. Furthermore, we require a comprehensive test suite to safeguard these profiling routines against future regressions.

When deploying local large language models using tools like Ollama on different hardware setups, users often notice a puzzling discrepancy in default behavior: a machine with ample memory or a specific profile defaults to a modest 4k context window, whereas another machine might default to 32k or require explicit tuning to avoid running out of VRAM. This variance isn't just a quirk of random initialization; it stems from how the runner estimates available memory budgets, accounts for weight footprints, and crucially, how it divides the total context budget across multiple concurrent execution slots configured via environment variables like OLLAMA_NUM_PARALLEL.

When you run multiple prompts concurrently, the KV cache requirements scale linearly or sub-linearly depending on batching, but the statically or dynamically allocated slots carve up the available context space. If a runner reserves memory for multiple parallel slots using a default context length, the resident memory footprint can hit a hard hardware ceiling—the memory cliff—causing sudden thrashing, out-of-memory errors, or unexpected fallback to slower CPU offloading despite the model file itself fitting comfortably within the device memory limits.

Your task in this exercise is to investigate this behavior by building a small diagnostic tool that models context defaults across machine profiles, computes the slot allocation breakdown based on OLLAMA_NUM_PARALLEL, and accurately predicts the memory cliff by comparing theoretical resident bytes against measured allocations. You will write code to parse context defaults, simulate parallel slot sharing, and implement rigorous regression tests to ensure your memory modeling correctly identifies when a configuration will trigger a cliff.

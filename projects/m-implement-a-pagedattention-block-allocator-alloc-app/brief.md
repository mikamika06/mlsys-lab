Our production LLM serving engine has started generating corrupted outputs during beam search, and we need your help to track down the root cause. A user opened an issue with a detailed trace log showing that beam 2's generated text suddenly contains a token ('banana') that was actually predicted and generated by beam 1. Beam 2's probability path never selected 'banana'.

To make matters worse, the user also provided a memory utilization graph showing that forking a single sequence into 4 beams immediately multiplies the KV cache usage by 4x. In a system implementing PagedAttention, forking a sequence should be nearly free in terms of memory, because the child sequences should share the same underlying KV blocks as the parent.

We suspect the KV cache block allocator is fundamentally broken. It might be doing eager deep copies on forks (explaining the memory spike), or even worse, it might be sharing block references but failing to perform a copy-on-write when a beam appends a new token. If two beams share a block and one writes to it without copying, it will silently clobber the other beam's history! Your task is to implement a robust PagedAttention block allocator with strict copy-on-write semantics.

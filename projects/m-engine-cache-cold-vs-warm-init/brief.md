We are observing severe startup latency spikes and redundant compilation overhead in our TensorRT execution provider pipeline when deploying updated models into production. Every time the service container restarts or when a new model variant is loaded with slightly different dynamic shape profiles or graph configurations, TensorRT initiates a full, costly re-compilation of the ONNX subgraph. This occurs despite having an engine cache directory configured and populated from previous runs.

Upon investigation, we notice that the generated TensorRT execution engines are being invalidated prematurely, forcing the runtime to fall back to building engines from scratch at inference startup. Additionally, some subgraphs are suffering from low node coverage because specific fusion patterns and custom operators are not being correctly registered or retained during subgraph partitioning, leaving large portions of the model to fall back to the default CPU execution provider.

We need to instrument our caching and partitioning layer to diagnose engine cache invalidation triggers, ensure that warm initialization paths correctly reuse cached engines without triggering recompilation, and enforce higher TensorRT node coverage thresholds. Your task is to implement the engine cache verification logic, trace the root cause of cache invalidation, and ensure that subgraph partitioning maximizes TensorRT node coverage.

Our serving engine exhibits severe tail latency degradation during the decode phase under high sequence lengths and large batch sizes. Profiling FlashAttention decode kernels indicates that while splitting the key-value context sequence across multiple threadblock groups (split-KV parallelism) improves occupancy for single-sequence or small-batch requests with long contexts, it causes noticeable slowdowns when applied indiscriminately at larger batch sizes.

Engineers report that the latency curve against `num_splits` turns non-monotonic as batch size scales up. Beyond a certain crossover batch threshold, the synchronization and global memory reduction overhead required to combine partial attention results across splits outweighs the benefit of parallelizing the sequence dimension. Additionally, because the serving engine uses paged KV caching with non-contiguous physical memory blocks, existing split planning routines fail to correctly align split boundaries to page block boundaries, leading to redundant memory accesses and unaligned kernel launches.

You need to implement a cost-modeling and split-planning module that accurately captures the `num_splits` latency curve, computes the crossover batch size where splitting ceases to be beneficial, and generates optimal split execution plans for paged KV cache physical block tables.

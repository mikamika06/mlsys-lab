# Ticket: Suboptimal TensorRT Execution Speed and Precision Fallback in Quantized Model Deployment

We are observing severe latency regressions and unexpected precision fallbacks when deploying our ONNX-quantized models through TensorRT engines in production. Specifically, after converting our transformer blocks and linear projection layers with explicit QuantizeLinear and DequantizeLinear (Q/DQ) nodes, profiling shows that certain layers fail to achieve hardware-accelerated INT8 execution paths. Instead of fusing the quantization and dequantization operations directly into the preceding or succeeding layers (such as convolutions or matrix multiplications), TensorRT is inserting explicit reformat, copy, or fallback layers into the execution graph. This results in heavy memory bandwidth overhead, unnecessary intermediate buffer allocations, and diminished throughput compared to native FP16 engines.

Additionally, our automated deployment pipeline lacks a robust validation mechanism to verify that per-channel quantization parameters (such as scale dimensions and axes aligned with weight tensors) are correctly placed around matrix multiplication operators before engine build time. When per-channel scaling factors are misconfigured or improperly broadcasted, the TensorRT builder silently defaults to lower-performing fallback configurations or produces numerical divergence against reference FP16 baselines.

We need engineers to implement a systematic module within our low-level tooling suite (`qfusion`) that accurately predicts whether a given Q/DQ pattern will result in successful fusion or reformat fallback, correctly inserts per-channel Q/DQ nodes around MatMul operations with proper axis alignment, and validates engine precision trade-offs between INT8 QDQ and FP16 execution modes. Furthermore, a rigorous regression testing framework must be established to catch any structural violations in Q/DQ placement prior to compilation.

An optimization team on the mixed-precision training track is auditing memory footprint and arithmetic performance of a custom transformer stack under PyTorch's automatic mixed precision (`torch.autocast`). Engineers noticed that while using `torch.autocast(device_type="cuda", dtype=torch.bfloat16)` reduces memory bandwidth pressure and speeds up matrix multiplications, certain critical paths or downstream submodules designed to enforce high-precision checks or numerical stability are wrapped inside nested context managers.

Specifically, the codebase uses `torch.autocast` blocks, but a troubling symptom has emerged during profiling: performance counters and custom telemetry logs show that operations inside a nested, explicitly disabled autocast region (`torch.cuda.amp.autocast(enabled=False)` or `torch.autocast(device_type="cuda", enabled=False)`) are still exhibiting reduced precision behavior or inconsistent execution speeds, or alternatively, the measurement utilities fail to accurately capture the exact speedup ratio and peak memory delta between pure FP32 baseline execution and active autocast operations under deterministic benchmarking conditions.

Your task is to implement the measurement utilities and core verification routines in the package to precisely profile the speed and memory differences between FP32 and autocast-bf16 executions, and to enforce and verify that a nested disabled autocast region strictly forces FP32 compute rather than falling back or inheriting parent autocast states. You must implement the configuration structures, benchmarking execution wrappers, and a robust regression test suite that proves nested disabling works as mandated by the low-level system specification.

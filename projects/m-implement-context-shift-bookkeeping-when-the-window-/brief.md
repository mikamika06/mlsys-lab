# Бухгалтерія зсуву контексту, коли вікно переповнюється

У логах довгих сесій (агентний цикл, що генерує токен за токеном без явного
кінця) трапляється одне з двох: або ранер падає, щойно кількість токенів у
кеші впирається в `n_ctx`, або наявний "костиль" просто відрізає найстаріші
токени пачкою — і разом з ними вилітає системний промпт на самому початку
послідовності. Через кілька кроків після цього модель тихо забуває свою роль
і інструкції, хоча зовні сесія й не впала.

Окремий репорт з capacity planning: пам'ять кешу порахували так, ніби кожна
модель — звичайна multi-head увага, хоча частина моделей насправді GQA з
меншою кількістю kv-голів. Під ці моделі зарезервували вдвічі більше пам'яті,
ніж їм насправді треба.

Треба зробити дві речі: коректний зсув вікна, який ніколи не чіпає захищений
префікс, і чесний підрахунок байтів кешу, який показує різницю між MHA і GQA
на тому самому контексті.

## Що ти пишеш

`ctxshift/bookkeeping.py`:

```python
discard_count(n_past, n_keep) -> int
simulate(n_ctx, n_keep, n_tokens) -> dict
```

Кеш містить не більше `n_ctx` токенів одночасно. Перші `n_keep` токенів, які
взагалі колись потрапили в кеш (наприклад системний промпт), захищені — їх не
можна витісняти ніколи, скільки б зсувів не відбулось. У всіх тест-кейсах
`n_ctx` гарантовано більший за `n_keep` із запасом (мінімум на 2), так що
завжди є що зсувати.

`discard_count(n_past, n_keep)` — скільки токенів прибрати одним зсувом, коли
кеш із `n_past` токенів переповнився: `n_left = max(0, n_past - n_keep)`,
результат — `n_left // 2` (цілочисельне ділення навпіл: звільняємо половину
того, що не захищене, а не все й не жодного).

`simulate(n_ctx, n_keep, n_tokens)` — прогнати `n_tokens` кроків генерації по
одному новому токену за крок, починаючи з порожнього кешу. Токенам
призначають зростаючі id: 0, 1, 2, ... у порядку появи. Перед кожним новим
токеном: якщо `len(resident) + 1 > n_ctx`, порахувати `discard_count` від
поточного `len(resident)` і `n_keep`, витіснити
`resident[n_keep : n_keep + n_discard]` (блок одразу за захищеним префіксом —
не сам префікс і не хвіст), і тільки після цього додати новий id в кінець.
Повернути:

```python
{"resident": [...], "evicted": [...], "shift_events": [...]}
```

де `resident` — id, що лишились у кеші під кінець прогону, `evicted` — усі
витіснені id за весь прогін у порядку витіснення, `shift_events` — список
довжини `n_tokens`, де `shift_events[t]` — скільки id витіснили саме на кроці
`t` (0, якщо на цьому кроці зсуву не було).

`ctxshift/memory.py`:

```python
kv_cache_bytes(config) -> int
mha_vs_gqa(config) -> dict
```

`config` — це `{"n_layers", "n_heads", "n_kv_heads", "head_dim", "n_ctx",
"bytes_per_element"}`. На кожну позицію контексту шар тримає ключі і значення
для кожної kv-голови: `2 · n_kv_heads · head_dim · bytes_per_element` байтів.
Разом на всю модель: `kv_cache_bytes = n_layers · n_ctx · 2 · n_kv_heads ·
head_dim · bytes_per_element`.

`mha_vs_gqa(config)` порівнює цю саму модель, якби вона була MHA
(`n_kv_heads == n_heads`), з тим, яка вона є насправді (GQA, `n_kv_heads` з
конфігурації) — на ОДНАКОВОМУ `n_ctx` і решті параметрів. Повертає
`{"mha_bytes", "gqa_bytes", "saved_bytes"}`, де `saved_bytes = mha_bytes -
gqa_bytes`.

## Як перевіряється

Грейдер рахує еталон сам: для бухгалтерії зсуву — на кількох комбінаціях
`(n_ctx, n_keep, n_tokens)`, для пам'яті — на кількох конфігураціях моделей
(включно з чистою MHA, де `n_kv_heads == n_heads`). Третій майлстоун — твій:
пишеш тест у `tests/test_regression.py`, а ми підміняємо `simulate` на таку
реалізацію, що витісняє токени від самого початку кешу, ігноруючи `n_keep` —
тобто зливає захищений префікс у витіснення. Твій тест має це побачити.

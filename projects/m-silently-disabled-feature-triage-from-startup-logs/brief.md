Engine logs show a persistent warning about attention kernel fallbacks during long-context generation, yet performance profiling reveals no degradation and memory usage remains identical between runs. Engineers investigating throughput regressions in our serving infrastructure noticed that when switching between different attention backends under strict resource bounds, certain optimizations—such as fused flash-attention kernels and paged block-table layouts—are silently disabled at startup if initialization checks fail or configuration parameters mismatch expected hardware flags.

Instead of raising a fatal exception or aborting startup, the runtime defaults to a slower fallback path without clearly surfacing the decision in high-level metrics or telemetry. This silent fallback masks underlying configuration issues, making it difficult to guarantee that dual-engine bake-offs run under equivalent memory footprints and optimization tiers. When comparing two distinct serving engines under equal KV memory constraints, even minor discrepancies in feature availability can skew benchmark results, invalidating throughput comparisons and latency percentiles across production clusters.

Your task is to build a triage module that inspects startup logs and engine metadata to identify silently disabled features, compute exact KV cache memory consumption for a bake-off between two engines under identical resource limits, and extract the complete backend support matrix through direct source inspection of the engine implementations. You will implement the core logic in `triage/analyzer.py`, `triage/memory.py`, and `triage/matrix.py`, and provide a robust test suite in `tests/test_regression.py` that catches altered fallback behaviors and incorrect support classifications.

Our serving cluster is currently hitting severe out-of-memory (OOM) faults during peak load when deploying both standard Grouped-Query Attention (GQA) architectures like Llama-3-70B and Multi-head Latent Attention (MLA) models like DeepSeek-V3. During incident post-mortems, the operations team discovered that our static memory allocation script relies on hard-coded byte estimators that completely fail to account for the actual tensor shapes, hidden dimensions, number of layers, KV head counts, and compressed latent dimensions specified in each model's configuration file. 

When routing requests between diverse model checkpoints, the system incorrectly calculates the per-token KV cache footprint. For instance, Llama-3-70B's standard KV cache consumption is vastly miscalculated against DeepSeek-V3's compressed latent representations, leading to severe memory over-allocation or sudden catastrophic fragmentation. Furthermore, when attempting to scale request concurrency under a fixed VRAM budget, the scheduler either rejects valid concurrent requests or accepts far too many, resulting in abrupt kernel panics and GPU crashes. 

We need a robust, programmatic bytes-per-token calculation module derived directly from model configuration JSON files. This module must accurately compute the exact per-token memory footprint for both GQA and MLA architectures, evaluate the precise cache ratio between them, and determine the maximum safe request concurrency frontier under strict VRAM budgets without relying on guesswork or hard-coded approximations.

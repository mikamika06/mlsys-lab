Our fine-tuning pipeline is repeatedly crashing with Out-Of-Memory (OOM) errors during the optimizer initialization step on our largest generative models. The infrastructure team recently transitioned our adaptation workloads from full parameter updates to parameter-efficient fine-tuning using LoRA, operating under the assumption that freezing 99% of the base weights would drastically reduce the optimizer state footprint and easily fit our jobs within a single node's VRAM limits. However, telemetry suggests the memory overhead has barely budged.

Some researchers suspect that PyTorch's AdamW implementation might still be lazily allocating momentum and variance tensors for the frozen base parameters, while others claim the memory bottleneck is systemic and want to switch everything to 8-bit quantized optimizers. We currently lack the exact low-level memory accounting to prove or disprove either theory.

Before making invasive architectural changes to our training loops, we need a precise profiling toolkit. We need a way to exactly measure the tensor bytes allocated within an optimizer's state dictionary to confidently compare a full fine-tuning configuration against a LoRA-only configuration. Additionally, we need functionality to compute the exact memory delta gained from switching to bitsandbytes AdamW8bit. Finally, we need a robust verification function that we can insert into our training hooks to rigorously assert that our QLoRA setups maintain strictly zero optimizer-state entries for all frozen base parameters.

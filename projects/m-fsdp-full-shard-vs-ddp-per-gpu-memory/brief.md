# Ticket 8841: Unexplained OOM and Sudden Performance Drops in Large Multi-GPU Training Runs

Our engineering team has encountered severe memory anomalies and unexpected training stalls when scaling our transformer language models across multi-GPU nodes using PyTorch's distributed backends. Specifically, when switching a 7-billion parameter model setup from a native data-parallel wrapper to a fully sharded data-parallel configuration, cluster operators observe drastic, non-intuitive shifts in peak per-GPU memory consumption that contradict standard linear scaling assumptions. Furthermore, asynchronous profiling traces captured via the PyTorch profiler display erratic communication patterns, long idle periods between backward execution steps, and frequent synchronization bubbles that completely stall the compute streams across different ranks.

Compounding these hardware utilization issues, application logs indicate a sudden surge in dynamic compilation overhead and frequent graph re-evaluations when specific optimizer splitting routines are enabled alongside gradient bucketing. Instead of executing smooth, fused parameter updates, the runtime frequently falls back to eager execution mode due to unexpected control-flow interruptions injected during gradient hook registrations and parameter flattening passes. These symptoms combine to severely degrade training throughput, causing intermittent out-of-memory crashes on rank 0 even when aggregate memory usage across all nodes appears well within safe operational limits. We need a diagnostic suite to model memory footprints precisely, classify these multi-rank trace patterns, and identify graph disruption sources.

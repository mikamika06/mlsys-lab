Сервіс тримає одну модель і працює. Щойно приходить другий запит паралельно — swap, потім OOM. Пам'яті нібито вдосталь. Треба тримати два одночасних запити на тій самій машині.

У нас розгорнутий локальний інференс-сервер для великої мовної моделі. Коли надходить перший запит, він успішно обробляється: модель завантажується в пам'ять пристрою, виділяється буфер під контекст (KV-cache), і генерація йде стабільно. Проте, як тільки надходить другий паралельний запит, починається активний витікання пам'яті у файл підкачки (swap), після чого система видає помилку Out of Memory (OOM) і аварійно завершує процес.

На перший погляд, загального об'єму оперативної пам'яті на ноді вдосталь для зберігання кількох копій чи додаткових буферів. Але на практиці сумарне споживання пам'яті під час паралельної обробки різко зростає через неправильне керування розподілом ресурсів, дублювання ваг або неконтрольоване розширення кешу контексту для кожного активного слота.

Нам необхідно провести глибокий аналіз реального споживання пам'яті, вивести точні формули залежності KV-кешу від довжини контексту та кількості слотів, знайти причину дублювання або перезавантаження моделі в пам'яті, підібрати оптимальні параметри конфігурації під обмежений бюджет обладнання та забезпечити стабільну роботу щонайменше двох паралельних запитів без використання swap. Також потрібно реалізувати надійний захисний регресійний тест, який гарантуватиме відсутність подібних проблем у майбутньому.

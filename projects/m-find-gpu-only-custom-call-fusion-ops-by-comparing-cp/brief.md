We are investigating a recurring production crash during the XLA compilation phase of our model training pipeline when switching from CPU evaluation/tracing to GPU execution. Recently, during a large-scale cluster rollout, certain model configurations compiled and ran successfully during dry runs on local CPU backends, but catastrophically failed deep inside the XLA backend compiler when targeting Nvidia GPUs. The failure manifests as an obscure backend compilation error or silent misbehavior during lowerings, rather than a clear JAX-level shape check error. Specifically, JAX's Python-side shape checker and abstract evaluation pass appear completely satisfied, allowing the model graph to be lowered to XLA HLO. However, once the HLO module is dispatched to the GPU compiler backend, it encounters mismatched dimensions, unexpected layout transformations, or unhandled fusion layouts inside custom-call operations that are injected exclusively for the GPU target. Engineers currently lack an automated way to systematically inspect and compare textual or structured HLO dumps between CPU and GPU execution traces to isolate which custom-call or fusion operators are missing or improperly shaped on the GPU backend before launching lengthy cluster jobs. We need a robust diagnostic utility to parse HLO artifacts, identify GPU-only custom-call/fusion anomalies by cross-referencing CPU versus GPU HLO trees, and catch these stealthy compilation regressions early.

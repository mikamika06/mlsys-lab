Our vLLM monitoring dashboard in Grafana went haywire during a recent canary deployment. First, the TTFT (Time To First Token) latency charts started displaying invalid quantile values after a metrics aggregation pipeline update, making it impossible to evaluate prompt processing latency during load spikes. Second, whenever a vLLM engine instance crashed or restarted, the throughput graph showed sudden massive negative spikes in completed requests per second, dropping total serving metrics below zero and triggering false SEV-1 alerts. Furthermore, our automated metric collector crashed whenever untyped scrapes or metrics without buckets were fed into the aggregation pipeline.

We need a robust, typed metrics processing module for our serving pipeline that can reliably parse raw Prometheus `/metrics` exposition text into structured metric families, correctly calculate high-percentile latency metrics like p99 TTFT with bounded linear interpolation error, and accurately compute request throughput rates across scrape intervals even when individual vLLM worker counters reset due to pod restarts. Finally, we need a regression test suite to ensure future metric collection refactors never break counter reset handling again.

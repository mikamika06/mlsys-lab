# Хто з локальних раннерів насправді підтримує який параметр

За одним ендпоїнтом `/v1/chat/completions` у нас стоїть кілька локальних
раннерів (кожен обслуговує свій пул моделей), а клієнтський код скрізь
однаковий — просто OpenAI SDK. Скарги приходять рандомно: у одного клієнта
`seed` перестав давати відтворюваність після перемикання на інший пул, у
іншого `tools` тихо не викликаються, хоча відповідь `200` і за формою
виглядає нормально. Окрема скарга від ops: нативна адмінка раннера показує
чергу і cache hit rate, а в моніторингу, що читає лише `usage` з відповіді
шима, цих чисел взагалі немає — по них можна було б побачити проблему
заздалегідь, а не постфактум.

Треба один раз чесно розписати, який параметр на якому раннері реально
працює, а який просто мовчки ковтається чи відсікається валідацією. І
окремо — які лічильники раннер веде нативно, а які губляться, коли
відповідь проходить через сумісний з OpenAI шим.

## Що ти пишеш

`oaicompat/params.py` — `classify_params(runner) -> list[dict]`. `runner` —
це `{"name", "supported": set[str], "ignored": set[str], "native_counters": [...]}`.
Є фіксований список із 15 параметрів `PARAMS` (уже в файлі). Для кожного
параметра з `PARAMS`, у порядку сортування за назвою:

- він у `runner["supported"]` → рівень `"supported"`;
- інакше він у `runner["ignored"]` → рівень `"ignored"`;
- інакше → рівень `"unsupported"` (раннер його не знає: передача такого
  поля або впаде валідацією, або в кращому разі буде проігнорована без
  жодної гарантії).

Результат — список `{"param": ..., "level": ...}`, по одному на кожен із
15 параметрів.

`oaicompat/counters.py`:

```python
native_counters(runner)   # усі лічильники, які раннер веде нативно
shim_counters(runner)     # лише ті, що потрапляють у стандартне поле usage OpenAI
hidden_counters(runner)   # native_counters мінус shim_counters
```

Стандартна OpenAI-схема `usage` — це рівно `OPENAI_USAGE_FIELDS` (уже в
файлі): `completion_tokens`, `prompt_tokens`, `total_tokens`. `shim_counters`
— це перетин нативних лічильників раннера з цією фіксованою множиною: шим
ніколи не показує клієнту нічого понад ці три поля, скільки б своєї
телеметрії раннер не тримав усередині. Усі три функції повертають
відсортовані списки без дублікатів.

## Як перевіряється

Грейдер рахує еталон сам, на своєму наборі раннерів. Третій майлстоун —
твій: пишеш тест, а ми підміняємо `shim_counters` на версію, яка віддає
клієнту взагалі все, що раннер бачить нативно. Твій тест має це зловити.

```
mlsys project start m-classify-15-openai-params-by-support-level-on-each-r
mlsys project grade m-classify-15-openai-params-by-support-level-on-each-r --milestone 1
```

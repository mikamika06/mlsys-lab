Our low-level machine learning stack is currently investigating how tracing overhead behaves across multi-stream execution and custom CUDA kernels, but the performance engineers are hitting a wall when trying to reconstruct precise temporal nesting from raw Chrome Trace event payloads. Specifically, when we pull trace files containing overlapping `B` (begin) and `E` (end) records generated by `record_function` instrumentation, the visual timeline and downstream profiling analysis tools completely break down. The nesting depth fluctuates wildly or collapses into flat tracks, completely losing parent-child block relationships.

Furthermore, we are experiencing critical discrepancies in how different event types are parsed. The trace payloads mix standard duration events (`X`), discrete instantaneous points, and explicit paired begin/end (`B`/`E`) markers. The semantics of the `ph` field are being misinterpreted, causing duration calculations for paired events to either double-count overlapping ranges or drop nested child executions entirely. To make matters worse, Kineto instrumentation exports process and thread metadata using internal process IDs and thread IDs (`pid`/`tid`) that appear as opaque numeric identifiers in the UI, failing to map back to the human-readable names assigned during model initialization or kernel launch configuration.

We need a dedicated, robust profiling module that can accurately rebuild execution nesting depth over time from raw `B`/`E` record function ranges, correctly classify `ph` field semantics to recover accurate event durations for both standalone and paired events, and parse Kineto process and thread metadata to map numerical identifiers to clean, human-readable track labels. Without this core capability, our performance regression tracking remains blind to nested execution bottlenecks.

Our automated performance monitoring pipeline for cluster-wide PyTorch jobs is producing unreliable metrics for multi-stream training runs. Dashboard reports show GPU utilization exceeding 100% on several nodes during distributed training steps, causing automated scaling alerts to fire unexpectedly. At the same time, performance engineers attempting to profile kernel launch overheads are seeing missing or negative launch-to-execution latency numbers in their reports.

To make matters worse, several nightly profiling runs that crashed mid-iteration due to host out-of-memory errors produced corrupted Chrome trace exports. The trace ingestion worker currently fails when processing these incomplete trace logs, either crashing with stack index errors or silently outputting garbled execution timelines that contaminate our long-term metric store.

We need a clean, robust trace processing engine in `gpuprof/` to handle Kineto JSON trace exports correctly. The ingestion module must sanitize incoming event sequences and flag truncated trace logs caused by missing end markers. The profiling tool must properly account for concurrent GPU streams when computing active device execution time rather than naively summing overlapping intervals. Finally, host-to-device event correlation must accurately measure kernel launch latency across all valid event pairs.

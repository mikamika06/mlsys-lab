The model serving team has been profiling our new hierarchical KV cache, and the latency numbers under load are brutal. We recently added an L3 SSD tier behind the host RAM (L2) and GPU HBM (L1), but our PCIe bandwidth is completely saturated. When we dump metrics, the actual write bandwidth used doesn't match our back-of-the-envelope calculations at all.

We suspect two separate issues are colliding. First, our admission policy is currently set to "always admit," meaning every time we read a key from the SSD, we prefetch it all the way up to HBM, evicting other active blocks. Second, we are currently forcing a write-through policy where every generation step immediately flushes KV blocks to all tiers, capping us at the L3 link's 10 GB/s limit.

We need you to build a rigorous three-tier cache simulator to model this before we rewrite the C++ serving engine. The simulator must accurately track read latency (accounting for tier-to-tier prefetch movement) and write penalties under different admission policies (always, reuse>=2, size-aware) and write strategies (write-back vs write-through). Only by baking off these configurations in the simulator can we figure out the correct default parameters for production.

An anomaly has been detected in our profiling pipeline. When running performance tracing on macOS environments, developers report significant discrepancies when attempting to measure the fine-grained runtime characteristics of our low-level inference routines. Specifically, using Python's built-in instrumentation profiler introduces massive, non-uniform distortion into execution paths, making it impossible to establish an accurate baseline. At the same time, alternative sampling-based profiling approaches exhibit different overhead profiles that must be carefully quantified and bounded before we can trust any performance regressions reported in our continuous integration pipelines.

Furthermore, when utilizing PyTorch's internal profiling utilities for deeper operator-level investigations, engineers frequently enable multiple telemetry flags simultaneously—such as recording tensor shapes, capturing Python stack traces, tracking memory allocations, and computing floating-point operations. Each of these configuration flags exacts a distinct performance tax on execution throughput. Without empirical measurements detailing the exact added overhead ratio contributed by each individual telemetry parameter, teams enable them indiscriminately, leading to severe slowdowns and distorted runtime measurements.

Your task is to implement an instrumentation vs sampling overhead analysis framework, quantify the throughput degradation ratios between cProfile and py-spy style sampling on macOS execution traces, and rank the additional overhead imposed by profiling flags (`record_shapes`, `with_stack`, `profile_memory`, `with_flops`) to ensure reliable performance tracking.

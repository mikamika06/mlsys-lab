We are experiencing a severe regression in our PyTorch model execution profiling pipeline. Recently, engineers running end-to-end training runs have noticed that standard summary tables produced by the framework's internal profiling tools do not accurately reflect the actual breakdown of compute versus kernel launch overheads when compared against raw Chrome tracing dumps exported during profiling sessions. Specifically, when we analyze the JSON trace files directly, the derived key averages and self-time aggregations show discrepancies compared to what is expected, particularly around kernel execution durations versus host-side queue delays and nested event durations.

Furthermore, performance analysts require a robust mechanism to compute the exact GPU busy fraction alongside idle gaps directly from the chrome trace event payloads, isolating periods where streaming multiprocessors are starved versus saturated. Additionally, as we iterate on model architectures and operator fusions, we lack an automated way to pinpoint the largest self-time regression between two distinct trace files—meaning regressions in specific CUDA kernels or operator categories are getting lost in aggregate averages across hundreds of thousands of trace events.

Your task is to build a low-level trace analysis toolkit in Python that parses raw Chrome trace JSON files, correctly aggregates self-times and key averages matching standard framework semantics, calculates precise GPU utilization and idle gap metrics, and provides an automated comparison tool to detect and isolate the largest self-time regressions between a baseline and a candidate trace. You will also write a comprehensive regression test suite that enforces these invariants and protects against faulty aggregation logic.

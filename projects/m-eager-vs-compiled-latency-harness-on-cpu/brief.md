An engineering ticket has been filed regarding latency profiling and compilation behavior of PyTorch models on CPU within our lower-level machine learning stack. The telemetry service reports that downstream modules attempting to benchmark standard PyTorch eager execution against various compiled backends (`torch.compile`) are encountering inconsistent timing metrics, unhandled graph-break exceptions, and improper fallback behaviors on standard CPU targets.

Specifically, when operators attempt to run latency harnesses comparing default compilation modes against specialized settings such as `reduce-overhead` or `max-autotune-no-cudagraphs` on CPU, the harness fails to isolate kernel execution times cleanly or correctly aggregate warmup iterations versus timed iterations. Furthermore, when engineers attempt to enforce strict graph capture by passing `fullgraph=True` on models containing unsupported control flow or dynamic operations, the exact compilation exceptions are either swallowed, misclassified, or incorrectly propagated, leaving the profiling suite unable to validate whether a model is fully graph-compatible.

Your assignment is to implement a robust Eager-versus-Compiled latency harness on CPU. This unit requires you to build a structured evaluation module that measures execution latency ratios across default, reduce-overhead, and max-autotune-no-cudagraphs modes, handles CPU-specific compilation constraints, enforces `fullgraph=True` graph capture validation, and provides comprehensive regression tests ensuring that compilation fallback flags and latency ratio invariants hold under varied execution workloads.

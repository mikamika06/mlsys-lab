We are running real Triton benchmarking on a GPU cluster and noticed that several custom kernels written for our fused attention and normalization layers are performing far below peak hardware capability. When looking at the roofline profile data exported from our benchmarking runs, the throughput numbers for these kernels look erratic, and the engineers on the performance team are unsure whether the bottleneck stems from arithmetic intensity being too low or the memory bandwidth being fully saturated.

Right now, we lack a clean programmatic way to take kernel metadata—specifically the recorded instruction counts, floating-point operations, byte read/write traffic, and the hardware specs of the target GPU—and automatically classify whether a given Triton kernel invocation is compute-bound or memory-bound based on its arithmetic intensity. Without this automated classification, we keep wasting engineering cycles tuning block sizes and register usage on memory-bound kernels that cannot possibly benefit from more compute throughput, and vice versa.

Your task is to build a lightweight analysis module that processes Triton kernel execution traces, computes arithmetic intensities, compares them against the hardware ridge point, and correctly classifies each kernel. You will also build a helper to extract memory traffic metrics and write a regression test suite that ensures your arithmetic intensity boundaries hold true under edge cases.

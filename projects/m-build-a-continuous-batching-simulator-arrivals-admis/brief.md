We recently switched to a new LLM inference engine that promised a 4x throughput increase out of the box, but our production metrics show we are barely getting a 1.2x bump. We ran a trace with highly skewed decode lengths—where some very short summarization requests are mixed in with extremely long generation tasks—and observed that the GPU is frequently underutilized during these workloads.

The system seems to be waiting for the longest request in a batch to completely finish before it takes in any new work, which effectively means it is falling back to a static batching strategy rather than dynamically scheduling new requests. We need a way to simulate both static and continuous batching behaviors using our historical request traces. Building this simulator will help us calculate the expected throughput ratio (continuous vs. static) so we can mathematically prove to the vendor that their engine is misconfigured. Additionally, we need to extract the per-step batch occupancy histogram from the engine's debug logs to verify if it is actually filling the available batch slots as other requests complete. If the histogram skews heavily towards 1 or 2 active requests despite a batch size limit of 16, it confirms our suspicions about their admission policy.

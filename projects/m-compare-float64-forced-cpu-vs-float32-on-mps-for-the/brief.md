Engineers working on low-level Apple Silicon deployment pipelines have noticed severe performance discrepancies and unexpected numerical shifts when moving workloads between execution targets. Specifically, computations that are forced onto the CPU using standard precision types behave differently compared to operations running directly on the Metal Performance Shaders (MPS) device.

When conducting micro-benchmarking of matrix operations and tensor reductions, performance leads observed that wall-clock time measurements for MPS kernels frequently report near-zero execution times or wildly fluctuating metrics. This happens because dispatching work to the GPU is asynchronous by nature, meaning the control flow returns to the host CPU before the hardware execution units finish computing the requested kernels. Without explicitly synchronizing the command queue, timing wrappers simply measure the dispatch overhead rather than the true workload duration.

Compounding this issue, developers need a reliable way to inspect device availability flags such as `torch.backends.mps.is_available()` versus `torch.backends.mps.is_built()` to understand the underlying runtime capabilities, especially when transitioning between simulated CPU fallback modes and native hardware acceleration. Your task is to build a robust diagnostic and verification module that correctly wraps these MPS capability checks, handles forced CPU vs MPS float32 execution profiling without falling into the asynchronous timing trap, and validates numerical invariants between execution targets.

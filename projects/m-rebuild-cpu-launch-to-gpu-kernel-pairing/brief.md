We are experiencing severe visibility gaps when analyzing PyTorch performance profiles generated from our deep learning workloads. During recent scaling runs on our multi-GPU training clusters, performance engineers attempted to trace kernel execution bottlenecks using raw Chrome trace JSON files and key_averages summaries. However, developers report that they cannot cleanly map high-level PyTorch operator launches on the CPU side to their corresponding low-level CUDA kernels executing on the GPU. Without a reliable pairing mechanism, identifying queue delays and host-to-device launch overheads is guesswork. Furthermore, automated scripts fail to categorize trace slices into meaningful operational buckets such as heavy compute, memory-bound kernels, or runtime overhead, making it impossible to aggregate profiles across large runs. Finally, attempting to compute achieved FLOP/s per matrix multiplication operator using metadata and with_flops data yields wildly inaccurate or missing numbers, preventing us from verifying hardware utilization efficiency. We need a robust, deterministic trace parsing and analysis library to bridge CPU launches, classify execution phases, and accurately compute per-operator FLOP/s metrics.

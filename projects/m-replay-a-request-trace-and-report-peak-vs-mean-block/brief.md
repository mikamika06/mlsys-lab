We are preparing a new low-level ML serving diagnostics pipeline for vLLM-style block allocations, and our simulation tooling is currently blind to the actual memory pressure experienced during a request workload. Right now, our scheduler accepts request arrival traces with block requirements over time, but it only spits out the final execution logs without giving us a granular breakdown of block usage metrics.

When we run heavy concurrent workloads through our paged attention engine, system operators report that peak memory allocation spikes drastically, causing unexpected out-of-memory crashes even when the average block occupancy across the entire run appears well within safe thresholds. Without a proper trace replay tool that calculates both the peak block usage and the mean block occupancy over time from a recorded sequence of active blocks per timestep, we have no way to tune our block pool sizes or catch capacity exhaustion before it brings down production nodes.

Your task is to build a replay module that consumes a request trace and a sequence of block allocations per timestep, computes both the peak and mean block occupancy metrics, and reports these statistics accurately. Specifically, you need to implement a clean trace replay parser, compute exact occupancy statistics across timesteps, and provide a regression test suite that guarantees your occupancy metrics remain robust and invariant under trace re-orderings or overlapping block allocations.

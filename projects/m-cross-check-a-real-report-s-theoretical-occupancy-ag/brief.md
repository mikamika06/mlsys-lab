We are currently investigating discrepancies between our automated profiling dashboards and manual performance audits for several core custom CUDA kernels deployed in our inference pipeline. During recent profiling sessions using Nsight Compute (`ncu`), engineers noticed that while high-level execution times are captured correctly, specific occupancy metrics reported under different sections appear misaligned or difficult to reconcile with hand calculations derived from kernel launch configurations, register counts, and shared memory allocations. Specifically, queries mapping raw hardware performance counter fields to their respective Nsight Compute reporting sections are failing or returning misplaced values, making it impossible to audit whether the GPU's Streaming Multiprocessors (SMs) are fully utilized. Furthermore, our current tooling lacks a rigorous cross-check mechanism to validate whether the reported Theoretical Occupancy matches the theoretical maximum calculated from hardware limits, register usage granularity, and block sizing constraints. Without a clean mapping module and a reliable hand-computation cross-check function that evaluates within tight relative error bounds, performance regression testing remains guesswork. We need a robust implementation that correctly maps raw counter names to report sections, computes theoretical occupancy precisely based on device specifications, and includes comprehensive regression tests ensuring these calculations maintain strict mathematical invariants under edge-case configurations.
